## Operational Boundaries

### Always

- **Run the check:** Run `npm run check` before completing a task. It checks formatting, builds the cheats bundle, runs the syntax checks, ESLint, the CSS checks and the schema check, then all tests. It runs on every push and pull request, and a red check blocks merging.
- **Guard against action bias:** If a reported bug cannot be reproduced or is already resolved by current code, report findings clearly instead of proposing speculative changes. Never invent modifications for working behavior.
- **Verification files:** Place temporary scripts and dumps in the system temporary directory or another authorized scratch directory outside the repository root. Remove files you created before validation and task completion; preserve unrelated files.
- **Target Chromium 87:** The Steam embedded client runs Chromium 87. Keep UI code and browser-injected code compatible with Chromium 87, or supply a verified fallback. ESLint enforces this for `src/cheats` and `src/ui` (`eslint-plugin-es-x`).
- **Game names:** Every game name the code uses (`events(N)`, `_customBlock_*`, `behavior.*`, `firebase.*`, `cList` lists and `gga` keys) must be in `scripts/game-names.json`, or `npm run check` fails. For a new name, run `npm run game-names:update`: it downloads the web game's code (about 26 MB), confirms every name exists, and rewrites the list. Commit the list with your change. The Game update watch workflow compares the live web game with this list every 3 hours and opens one issue per game version that breaks a name or changes a function the code hooks.

### Ask First

- **Opening Pull Requests:** Never create, open, or push a pull request without explicit user confirmation.
- **Adding dependencies:** Check with the user before adding packages to `package.json`.
- **Config schema changes:** Ask before modifying `src/ui/config/optionsAccountSchema.json`.

### Never

- **Never edit protected paths:**
    - `config.js` and `src/ui/config/configDescriptions.js`: generated by `npm run config:generate` from the `defineCheat` rows' `config` and `src/modules/config/coreSettings.js`; change those and regenerate. Put user overrides in `config.custom.js`.
    - `src/ui/vendor/`: Upstream vendored libraries (VanJS). Do not modify directly.
    - `.scratch/`: Local artifacts and notes. Never stage, commit, or clean up unrelated files.
- **Never change lint ignores for temporary files:** Relocate or delete your temporary files instead of adding filename-specific exceptions to `eslint.config.mjs`.

## Verification & Testing

- **Automated tests:** `npm test` runs every `scripts/**/*.test.mjs` with Node's built-in test runner. No Jest, Vitest, or Mocha runner is configured.
- **Pre-completion check:** Run `npm run check` (formatting, then `npm run validate`: cheats bundle, syntax, ESLint, UI imports, CSS and schema, then `npm test`).
- **Manual live check:** Start with `npm run start`, attach to the running game client, and verify live behavior. Hot reload is not supported; restart the app to test backend and cheat modifications.
- **UI verification:** Use DOM assertions for text, visibility, loading, and action feedback. Inspect the injector UI target separately from the game target; use screenshots from a supported top-level target for visual layout checks.
- **Ad-hoc checks:**
    - Syntax check: `node --check path/to/file.js`
    - Account schema validation: `node -e "require('./src/ui/config/optionsAccountSchema.json')"`

## Architecture & Conventions

### Cheats Engine & Hooks (`src/cheats/`)

- **Runtime context:** `cheats.js` is bundled via Rollup from `src/cheats/` (ES modules) into an IIFE executed in the game's browser context (`window.__idleon_cheats__`).
- **Runtime contracts:** After `gameReady()`, access `gga`, `behavior`, `events`, `itemDefs`, and `cList` directly.
  Access registered cheat namespaces directly once their registration module has run.
- **Guards and fallbacks:** Use guards and optional chaining only when absence is possible on the actual execution path.
  Verify that fallback behavior preserves the feature; missing guaranteed bindings are initialization errors.
- **Verification fixtures:** Preserve real module-registration, readiness, and listener-binding order.
  Fix fixtures that omit guaranteed initialization rather than adding production guards to accommodate them.
- **Companion data:** `w1.companion.companions` is a comma-separated string (e.g. `"0,1,2"`), not a function or array.
- **Code simplicity:** Inline small 1–2 line logic at call sites rather than creating tiny single-use helpers. Use direct property access when types and shapes are guaranteed by the execution path.
- **New cheats:** Add a file in `src/cheats/cheats/` that calls `defineCheat` (copy `cheats/_example.js`); the build finds it, so no list needs editing. Its settings go in the row's `config` with a default and a description; then run `npm run config:generate`.
- **New game hooks:** Add a file in `src/cheats/hooks/` that calls `defineHook` (copy `hooks/_example.js`); the build finds it, so no list needs editing. Its handler is base-first by default.
- **Base-first hooks:** A method hook's handler gets the game method's result (`base`) after the game's method ran, so its side effects are kept:
    ```javascript
    defineHook({ id: "godlike.reach", target: () => events(12), method: "_customBlock_PlayerReach" }, (base) =>
        cheatState.godlike.reach ? 666 : base
    );
    ```
    Declare `around: true` only when that can't work (skipping the game's method, changing its arguments, or changing state it reads while it runs), with a one-line `// Around:` comment right above it saying why. Hooks on the same method wrap in declaration order (first is innermost); keep them in one file.
- **Game data hooks:** Hook a property of game data with `defineHook({ target, property }, ...)` (an accessor) or `proxy: true` (a Proxy in the property's place); see `core/hooks.js`. Don't patch the game with `new Proxy`, `Object.defineProperty` or assignment outside a hook.

### The 3.0 Rules (`scripts/rules/`)

Rule tests read the code and refuse the pre-3.0 ways of doing things; each refusal names the 3.0 way:

- **Patching the game:** only with `defineHook`. No `new Proxy`, `Object.defineProperty`, assigned functions or `_isPatched` outside `src/cheats/core/`.
- **Code from strings:** no `eval` or `new Function`.
- **`window`, routes, globals and dependencies:** belong to the core. Game-side mods read the game through `core/globals.js`; UI code doesn't add globals.
- **Network:** code that runs in the game (`src/cheats`) makes no network calls.
- **Loops:** declare them with `defineAutomation`. No `setInterval`, `setTimeout` or `requestAnimationFrame` on the game side outside the core.
- **Page saves:** through `writeVerified` (`writeManyVerified` for many), never `gga(path, value)` or `ggaMany` directly.
- **Imports:** mods (a cheat, hook or automation file with its folder, or a page folder) don't import each other; shared code goes in `src/cheats/helpers/` or the page building blocks. Nothing imports across the game (`src/cheats`), the server (`src/modules`) and the UI (`src/ui`).
- **Errors:** throw an `Error`; never return an `"Error: ..."` string.
- **Pages:** live in `src/ui/pages/<world>/<page>/` with `definePage`, not in the old tab lists (`Account.js`, `W2Tab.js` to `W7Tab.js`).
- **Around hooks:** each `around: true` hook has an `// Around:` comment right above it saying why base-first doesn't work.

`scripts/rules/exceptions.json` lists the permanent exceptions (`allowed`, each with its reason) and the code still to convert (`oldStyle`). New code never goes on either list. When you convert listed code, lower its count or remove it; the test fails until you do, so the list only shrinks. 3.0 ships when `oldStyle` is empty.

### Haxe Objects & Traversal

- Legends of Idleon is compiled with Haxe, which wraps object properties in an `.h` field.
- **Traversing objects:** Use `traverse(obj, depth, worker)` from `src/cheats/utils/traverse.js`. It automatically unwraps `.h` properties.
- **Manual property access:** Check `.h` when inspecting raw objects directly (e.g. `item.h.ID`).
- **Path discovery:** Use the UI Search tab to inspect live memory access paths, and the Monitor tab (`window.monitorWrap`) to track value changes.
- **Account-option defaults:** Before parsing an `OptionsListAccount` entry, establish its feature-specific initial values. Normalize known uninitialized values such as `0`, `null`, or `undefined` to the expected empty representation; reject unexpected values.

### Game Calculations

- **Calculation accuracy:** Trace the base formula, modifiers, caps, and the game's display formatting before porting a calculation. Match effective values and rounding to the game, then compare the result with an in-game display or read-only live state.

### UI & VanJS Reactivity (`src/ui/`)

- **Child reactivity:** When returning elements from a reactive child function `(() => condition ? a : b)`, return a single container node such as `div(a, b)` or `span(a, b)`. Returning a raw array `[a, b]` causes VanJS to stringify elements into `[object HTMLSpanElement]`.
- **Input focus preservation:** Keep `<input>` elements static and bind their value property to state (`value: state.val`). Wrapping inputs in reactive closures `(() => input({...}))` causes DOM re-creation and loss of focus on every keystroke.
- **Reactivity scope:** Keep reactive functions as tight as possible. Wrap only dynamic leaf elements (e.g. `div(table(thead(...), () => tbody(...)))`) rather than whole tables or parent containers.
- **Stable row identity:** Editable rows (`EditableNumberRow`, `ClampedLevelRow`, `useWriteStatus()`) require stable DOM identity. Re-rendering entire parent sections destroys button state and flash feedback. Use stable containers with `createStaticRowReconciler(...)` and update row values after load.
- **Initial loading:** Account tabs using `useAccountLoad` must invoke their loader during component initialization so opening the tab loads data without a manual refresh.
- **Write cancellation:** Return `{ cancelled: true }` from a `useWriteStatus().run(task)` task when the user cancels or no changes are needed. Use the native cancellation handling instead of `false` returns with `successState: null` workarounds.
- **Row bindings:** Bind reactive attributes through VanJS tag properties. Do not create imperative `van.derive` effects or attribute setters inside row reconciler mappers.
- **Saving edits:** Values save on Enter or on leaving the field, through the shared rows or `useAutoSave` with its `SaveState` (saving…, a ✓ once read back, or the reason). Pages add no SET or SAVE buttons. Keep fields and row buttons enabled while a save runs, so focus stays where the player put it.
- **Accessible feedback:** Action buttons must expose saving, success, and failure feedback to assistive technology. Avoid redundant `aria-label` values that mask changing visible text.
- **Before a UI PR opens:** for every `await` in a changed click, save or load handler, answer these four, with file and line. Most review findings on this repo's pages are one of them.
    - While the page waits for the game: what if the player clicks again, types something newer, or an older answer arrives last?
    - After a save or undo ends, worked or not: does the page read the game again, instead of putting back a value it remembered?
    - Is the thing the player was asked about still the thing that gets changed (character, world, selection)?
    - Is each failure said where it happened, cleared by the next success, and safe to try again?
- **Styles:** Put static layout, sizing, typography, and colors in `src/ui/styles/`. Reserve inline styles for dynamic CSS custom properties and necessary runtime coordinates.
- **Icons:** Use SVG icons from `src/ui/assets/icons.js` for decorative imagery instead of emoji glyphs. Keep mathematical symbols and ordinary text when they convey meaning.

## Git & PR Workflow

- **Contributor rules:** [CONTRIBUTING.md](CONTRIBUTING.md) is the source: new cheats and new game hooks need an approved issue before work starts; the core (`.github/CODEOWNERS`) is the maintainer's alone; one kind per PR; fill in the three-line PR template, including the in-game test the contributor did themselves. The `rules` check holds every PR to the first two, the maintainer's and AI-written ones included.
- **PR title:** PRs are squash-merged, so the title becomes the commit and a check enforces `<type>(<scope>): <short imperative description>` (`feat`, `fix`, `refactor`, `chore`, `test`, `docs`, `style`; the rule is `scripts/pr-title.mjs`). Lowercase description, no trailing period. Example: `fix(ui): restore sidebar content after switching tabs`. Use the same format for commits; branch names and in-PR commit messages aren't checked.
- **Pull requests:** Require explicit user confirmation before creation. Omit testing logs and validation details from PR descriptions unless requested. In PowerShell, use single-quoted here-strings or body files to prevent backticks from escaping Markdown.

- **Scope:** `docs/` records architecture, domain language, and decisions. It does not duplicate code behavior.
